# 一起完善数学思考伙伴

欢迎从一个具体问题开始贡献：修正一处条件、解释一道题为什么这样做、补充一项自拟任务，或者让一次查询更稳定。本文件是拟公开仓库的贡献约定草稿；正式发布后的交流渠道以该仓库的 Issue 与 Pull Request 为准。

先阅读 [README](README.md)、[数据结构](docs/DATA_MODEL.md)及[许可候选与材料范围](LICENSE_POLICY.md)。候选包提供工具、学习文档和原创演示，不含研究包的教材材料。

## 可以贡献什么

| 类型 | 有价值的改动 | 随附说明 |
|---|---|---|
| 数学纠错 | 补充分母非零、区间、取等条件，修正漏解或证明缺口 | 原记录、修改理由、完整适用条件 |
| 知识关联 | 改进前置知识、易混关系、题目与概念映射 | 关系两端 ID、方向、为什么相关、来源类别 |
| 思想卡与原创题 | 用具体任务说明转化、分类讨论或反例 | 自拟/改编来源、参考解、适用条件、迁移任务 |
| 学习流程 | 调整提示节奏，使学生能完成实质步骤 | 场景、修改前后对话片段、预期行为 |
| 数据与工具 | 修复查询、稳定 ID、改进公开导出和可复现性 | 最小复现步骤、实际验证结果、输入保护说明 |
| 体验与测试 | 发现无法读到资料、提前泄露答案或错判掌握 | 测试条件、实际回答、具体失败点 |

“方法”与“数学思想”分别组织。一个方法标签存在，并不说明相应思想已经讲清；一条新的关系也需要可解释的理由。

## 提交一次清楚的改动

1. 选择一个目标。数学纠错、结构调整和界面改动尽量分别提交，让评阅者能判断每项改变的原因。
2. 保留原记录身份。已有 ID、来源版本和页码不能因排版或分类调整而变化；更正内容时记录理由。
3. 核对相关条件。数学变更给出足以检查的推导或反例；学习流程变更用一段具体对话说明学生会做什么。
4. 运行针对性验证。只报告实际执行的结果。草稿中尚无的脚本不能写成已经运行成功。
5. 在变更说明中列出影响范围、来源与公开依据、验证结果、剩余问题。

涉及查询修复时，正式引入工具后应复跑对应命令；涉及数据库重建时，在新输出中检查教材和中考表及视图是否完整；涉及公开导出时，同步检查 JSONL、Markdown 和 SQLite payload，避免排除的材料仍保留在另一种形态里。

## 新增学习材料的检查项

- 题目自洽，答案和理由可核对，条件足以支持结论。
- 明确是自拟、教材整理还是教学归纳，不给自拟题编造教材页码或真题年份。
- 学生至少完成一个实质步骤；必要时允许 AI 示范，不让学生无限猜测。
- 自查任务与参考解分开，首轮不提前泄露答案。
- 迁移任务确实改变了一个关键条件、结构或目标；记录帮助发生的位置。
- 署名、来源与许可范围可以说明；不将第三方材料默认纳入项目候选许可。

可参照[学生任务](examples/STUDENT_TASKS.md)、[参考解](examples/DEMO_PACK.md)和[学习测试](evals/README.md)。模拟对话与测试设计可以帮助讨论，但不能代替实际运行或真实学习表现的记录。
